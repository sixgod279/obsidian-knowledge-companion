# 知识状态规范

以下技术内容和日期均为格式示例，不代表用户真实项目；时间按配置时区填写并附 UTC 偏移。

## 状态块格式

经验知识和待入初稿中的每个知识性段落使用一个 Obsidian callout。一个状态块表达一个原子结论；不要在同一块混合不同状态的结论。

### 事实

```markdown
> [!kb-fact] 事实 | 记录: 2026-08-12 14:20 +0000 | 核验: 2026-08-12 16:05 +0000 | 方式: 实机测试
> 在固件 V2.3、硬件 Rev.C 上，退出 STOP 模式后必须重新使能 USART2 时钟，否则串口不会继续接收。
> 证据: 测试编号 HW-20260812-03；恢复时钟后连续 100 次唤醒均通过。
```

要求：结论已被当前代码、原始资料、日志、编译、软件测试、实机测试或用户明确确认支持。必须写 `记录` 和 `核验`；说明核验方式，并尽量引用证据。编译通过只能证明构建，不等于功能已验证。

### 未验证

```markdown
> [!kb-unverified] 未验证 | 记录: 2026-08-12 14:20 +0000 | 复核期限: 未定
> 怀疑低功耗返回路径漏掉了 USART2 时钟恢复。
> 待验证: 在唤醒函数设置断点并观察 RCC 寄存器和 USART2 接收中断。
```

要求：用于假设、推断、尚未执行的方案和证据不足的用户陈述。必须写 `记录`，并尽量给出可证伪的下一步。不得把它作为确定操作指导。

### 错误

```markdown
> [!kb-error] 错误 | 记录: 2026-08-12 14:20 +0000 | 判错: 2026-08-12 15:10 +0000 | 学习价值: 保留
> “USART2 外设损坏”这一判断错误；更换芯片后现象不变。
> 错误原因: 只依据无接收现象下结论，未检查低功耗后的时钟门控。
> 正确结论: [[STOP模式退出后USART2时钟恢复]]。
```

要求：用于已经证伪的结论、无效做法或错误操作。必须写 `记录`、`判错` 和证伪依据。`学习价值` 只能是 `保留` 或 `可删除`；归档前没有充分理由时默认保留。

### 过时

```markdown
> [!kb-outdated] 过时 | 记录: 2025-11-03 10:00 +0000 | 判定: 2026-08-12 16:20 +0000 | 原适用: 固件 V1.x | 现适用: 固件 V2.0+
> V1.x 需要唤醒后手动恢复 USART2 时钟；V2.0 起统一由 PowerResume() 完成。
> 替代: [[V2电源恢复流程]]。
```

要求：结论过去在明确范围内有效，但现在的版本、硬件、环境、时间或流程已改变。必须保留原适用边界、判定日期和替代信息。日期较早本身不是过时证据。

## 文档 Frontmatter

Markdown 知识文档至少使用：

```yaml
---
type: experience
title: STOP 模式退出后 USART2 不接收
created: 2026-08-12 14:20 +0000
updated: 2026-08-12 16:20 +0000
project: 示例项目
topics:
  - 低功耗
  - USART
scope:
  firmware: V2.3
  hardware: Rev.C
sources: []
---
```

`type` 使用 `experience`、`source-note`、`decision`、`preference`、`index`、`index-proposal` 或 `daily-inbox`。Frontmatter 描述整篇文档，不替代段落状态。

## 哪些内容需要状态块

需要：技术结论、现象描述、判断、做法、配置值、偏好、决策、验证结果、失败经验、资料摘要。

不需要：标题、目录、纯链接列表、标签、Frontmatter、无语义的分隔符和模板提示文字。

表格中若多行状态不同，增加 `状态`、`记录日期`、`核验/判定日期` 列；若整张表同一状态，可将整表放入一个状态 callout。图片或二进制资料本身不改写，在旁注 Markdown 中对关于它的每个判断加状态块。

## 状态迁移

更新状态时保留证据链：

| 原状态 | 新状态 | 必要依据 |
|---|---|---|
| 未验证 | 事实 | 新的核验方式、日期和证据 |
| 未验证 | 错误 | 证伪测试或明确反证 |
| 事实 | 过时 | 适用边界变化及替代项 |
| 事实 | 错误 | 足以推翻原事实的新证据及更正原因 |
| 错误 | 过时 | 不建议；通常保留错误状态并补充适用背景 |
| 过时 | 事实 | 仅在旧环境重新成为当前适用环境时，新建或拆分事实块 |

状态变化时更新文档 `updated`，不要静默覆盖旧结论。对有学习或审计价值的变化，在正文保留“更正记录”状态块；仅无价值的笔误可以直接改正。

## 冲突时的可信顺序

1. 当前直接证据：当前代码、当前日志、当前硬件实测和用户本轮明确确认。
2. 与当前范围一致且有证据的 `事实`。
3. 原始资料；仍需检查资料版本和勘误。
4. `未验证`，只能作为排查候选。
5. `过时`，只能用于其原适用范围或历史解释。
6. `错误`，只能作为纠错经验，不能作为操作指导。

可信顺序不能代替适用范围判断。芯片手册的事实可能不适用于另一型号，实机结果也不能无条件推广到其他硬件版本。
