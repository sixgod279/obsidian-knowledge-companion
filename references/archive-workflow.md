# 归档工作流

## 1. 健康检查与清单

先运行 `health`。存在 `PREPARED`、`SNAPSHOT_CREATED`、`MUTATING` 或 `VALIDATED` 的未完成事务时，先根据事务清单继续或回滚；不能在半归档状态继续普通检索。

运行 `check-archive` 获取 `pending_dates` 和建议清单。自动归档包含所有过期日期及今天事务开始前已有的文件；主动归档包含全部非模板待入文件。清单生成后不再吸收新文件。

## 2. 取得归档事务

使用稳定的会话 UUID 作为 owner：

```powershell
python scripts/vault_tool.py --config "<CONFIG_PATH>" begin-transaction --mode archive --owner "UUID" --path "待入文件1" --path "待入附件2"
```

脚本取得 `00-检索层`、`10-资料层` 独占锁和清单内待入锁，在 Vault 外建立快照，记录每个现有文件的 SHA-256，并返回事务 ID。若任何锁冲突或哈希在快照时改变，事务不得开始。

所有修改、移动和删除都限制在事务声明的路径及明确新增目标内。新增受影响路径时先运行 `extend-transaction` 取得锁和快照。不要直接绕过事务改写上两层。

## 3. 机器审计和候选召回

运行：

```powershell
python scripts/vault_tool.py --config "<CONFIG_PATH>" scan
python scripts/vault_tool.py --config "<CONFIG_PATH>" candidate-search --query "当前主题、项目、器件、版本和现象" --limit 20
```

`scan` 检查哈希重复、规范化正文重复、标题、链接、状态字段、目录来源哈希和孤立资料。`candidate-search` 综合 BM25、标题、项目/范围、状态、实体、路径和 Wiki 链接关系召回候选。字符片段只能作为弱补充信号。

Codex 只深读清单主题相关的候选全文，并为每一对给出一种结论：

- `完全重复`：内容和有效元数据相同；
- `语义重复`：表达不同但主题、结论、范围和证据实质相同；
- `版本并存`：结论随版本、硬件、时间或环境不同且各自有价值；
- `真实冲突`：同一范围内结论不相容；
- `无关`：召回信号相似但知识无关。

只有前两类可以合并。分数本身永远不能授权合并。

## 4. 整理和写入

- 同一问题的多份初稿合成完整事件记录，不同问题保持独立。
- 原件归入 `10-资料层/01-原始资料` 并建立旁注；经验归入 `10-资料层/02-经验知识`。
- 版本并存时明确各自适用边界；真实冲突在证据不足时保留并标记待验证。
- 无学习价值的明确错误、完全重复副本和无效临时产物移入事务隔离，不立即永久删除。
- 冻结清单中的旧待入文件必须被资料层吸收或移入事务隔离，不能留在原路径后提交。未解决问题可带着`未验证`状态归入资料层；后续进展再建立新的当天待入笔记。
- 将索引修订建议与当前来源全文重新核对；只有来源和旧索引哈希仍匹配时才直接采用，否则重新生成。
- 目录项必须准确且充分，包含关键词、项目/范围、状态摘要、来源哈希、摘要、更新时间、资料和相关链接。

每次真正落盘前复核事务记录的旧 SHA-256。若与当前文件不符，说明 Obsidian 或另一进程已修改文件：停止覆盖，把拟写内容保存为冲突候选，并由 Codex比较双方后重新计划。

写入使用同目录临时文件、刷盘后原子替换。移动和删除先进入事务隔离区。每个操作追加到事务日志。

## 5. 验证与提交

重新运行 `scan` 并检查：

- 索引链接有效，来源哈希与正文一致；
- 新资料都有一个或多个有效目录路由，不存在意外孤立资料；
- 没有意外完全重复；
- 状态块格式正确；
- 事务清单内容已经吸收或明确保留；
- 归档期间新增的当天文件没有被误纳入。

将事务推进到 `VALIDATED`，再提交到 `COMMITTED`。只有 `COMMITTED` 后才能写归档成功状态并释放锁。失败则执行回滚或保留事务供下次继续；不得伪造成功。

恢复快照和隔离文件位于 Vault 外部运行目录，7天后由 `cleanup-runtime` 清理。未完成事务及其恢复数据永不按期限自动清理。
